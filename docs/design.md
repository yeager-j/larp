# LARP design (settled 2026-09-22)

> Historical v1 document. The Implementer workflow and three-round limit below are superseded by [ADR 0003](./adr/0003-planning-ends-with-desktop-handoff.md): planning now ends with a Codex desktop handoff, and new Runs allow five review rounds. See README.md for current usage.

Vocabulary is in [CONTEXT.md](../CONTEXT.md). Decisions with trade-offs are in [docs/adr](./adr). This file is the compact list of what was decided, for whoever builds it.

## Shape

- The `larp plan` process is the Relay. It holds the Run's Message queue, starts one Turn at a time, waits for the process to exit, reads its structured output, enqueues it, repeats. No daemon, no nesting, no polling.
- A Turn is a harness process. First Turn: `claude -p --session-id <uuid>` or `codex exec`. Later Turns: `claude -p --resume <uuid>` or `codex exec resume <thread-id>`. The Claude UUID is generated by larp; the Codex thread ID is read from the `thread.started` event.
- The Turn's structured final answer is the Message (ADR 0001). Claude: `--json-schema`, read from the `result` event's `structured_output`. Codex: `--output-schema <file> -o <file>`, read from the `-o` file, which holds only the last message.
- Exactly one active Turn per Run. A Participant may use its harness's own subagents inside a Turn.
- The Human can type a Message to any Role active in the current Phase at any time from the TUI. It is appended to the log at once and delivered inside that Role's next Envelope; it never starts a Turn on its own. Phase changes wait at a Gate for the Human.
- LARP touches no git and no repository files (ADR 0002).

## `larp plan` workflow

Roles: Planner, Reviewer, Implementer. Each is one model on one harness, chosen in the picker or by flags.

Phases:

1. **Planning.** Planner receives the task, replies `{kind: request, body, plan}`. Relay writes `plan` to `~/.larp/runs/<run-id>/plan.md`. Reviewer reads the file, replies `{kind: feedback | approve, body}`. Planner may reply `{kind: question, body}` only for product behavior, scope, external authority, or irreversible actions. Loop until `approve` or 3 rounds.
2. **Gate.** Shows the plan path and the last feedback. Human chooses: approve, send a Message to the Planner (stay in planning, reset the cap), or abort. Human may edit the plan file by hand first.
3. **Implementing.** Implementer receives the task and the plan path, replies `{kind: question, body}` or `{kind: done, body}`. Planner answers questions with `{kind: feedback, body}` or escalates with `question`. `done` ends the Run.

A reply carries `kind` and `body` only (plus `plan` for the Planner). The recipient is fixed by the pair (Role, Kind), so the model never chooses it and no invalid move is expressible:

| Role | Kind | Recipient |
|---|---|---|
| Planner | request | Reviewer |
| Planner | feedback | Implementer |
| Planner | question | Human |
| Reviewer | feedback, approve | Planner |
| Implementer | question | Planner |
| Implementer | done | Human |

Schemas are per Role and enforced by the harness. No `plan_path` field; the Relay owns the plan file.

## Gates

Two kinds, with different actions, both recorded in the log so `resume` lands on the same Gate.

- **Phase Gate** (after `approve` or the round cap): approve, message the Planner, abort.
- **Failure Gate** (after a harness error or a second schema failure): retry the same Turn, retry with a note to that Role, abort. Approving is not offered here.

## Envelope

Every delivered Envelope states that larp is relaying, then lists each Message it carries with sender Role and model, Kind, and body. It gives the absolute plan path once one exists and a one-line reminder of the reply schema. The first Envelope to each Role also carries the original task text. When a Human Message is waiting for the same Role, it rides in the same Envelope. The role prompt describes this protocol up front; it is prepended to the first Turn's prompt on both harnesses and, on Claude, also passed via `--append-system-prompt` on every Turn.

## Permission profiles

| Role | Claude | Codex |
|---|---|---|
| Planner, Reviewer | `--permission-mode plan --permission-prompts none --tools Read,Glob,Grep,ToolSearch,Skill,Agent,Write --allowedTools Read,Glob,Grep,ToolSearch,Skill,Agent --disallowedTools Bash,Edit,NotebookEdit,ExitPlanMode` | `-c sandbox_mode="read-only"` |
| Implementer | `--dangerously-skip-permissions` | `-c sandbox_mode="workspace-write"` |

Common to every Claude Turn: `--settings '{"disableAllHooks":true}' --effort <level> --model <model> --output-format stream-json --verbose --json-schema <schema>`. Common to every Codex Turn: `--json -m <model> -c model_reasoning_effort="<level>" --output-schema <file> -o <file>`, prompt as the positional argument, stdin closed. The working directory is set on the child process for both harnesses, since `codex exec resume` has no `-C`. Per-Role, per-harness extra args and the effort level come from `~/.config/larp/config.json`; defaults are effort `high`, no extras.

## Failure paths

- Output fails the schema: one retry with an Envelope saying so, then a Failure Gate.
- Non-zero exit, `is_error`, auth or model-access errors: straight to a Failure Gate showing stderr. No automatic retry.
- The plan file is written before the Planner's Message is appended, and `resume` rewrites it from the latest `request` in the log, so the file can never lag the log.
- No Turn timeout in v1.

## Persistence

`~/.larp/runs/<run-id>/` holds `run.json` (task, Participants, session IDs), `messages.jsonl` (append-only log, source of truth), `plan.md`, and per-Turn raw output. The log records every Message, every Human action (approve, abort, retry, notes), and every failure the Relay observed, so folding it through the reducer yields the current Phase. `larp resume <run-id>` continues from the log.

## CLI

- `larp config` refreshes the model list and sets the default Participant for each Role.
- `larp plan [task]` uses the defaults, `--pick` opens the pickers, and `--planner <harness>:<model> --reviewer … --implementer …` overrides for non-interactive use.
- `larp resume <run-id>`
- `larp runs`
- `larp show <run-id>`

## Rendering

Both event streams are mapped to one log: `Planner · claude-fable-5-1 · Read src/foo.ts`. `--quiet` prints only Messages and Gates. TUI pickers use `@clack/prompts`.

## Config

`~/.config/larp/config.json`: explicit model-to-harness list shown in the picker as `gpt-5.6-sol (codex)`, default Participant per Role, per-Role effort and extra args. It is written only by `larp config`, never seeded silently. `larp config` reads the Codex list from `~/.codex/models_cache.json` (Codex refreshes it on every run and stamps a fetch time, which is shown); neither CLI can list models on demand, and Claude has no list at all, so the Claude side is a built-in list plus free-text entry that the first Turn validates.

## Out of scope for v1

Generic user-defined workflows, parallel Turns, Turn timeouts, `codex queue` or live-session adapters, git branches or worktrees, a `larp send` command.
